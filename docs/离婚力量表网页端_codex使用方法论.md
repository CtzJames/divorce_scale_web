# 离婚力量表网页端项目 Codex 使用方法论

## 一、文档目的

本方法论文档用于解决以下问题：

1. 在“离婚力量表网页端”项目后续开发中，如何判断当前 Codex 任务是否应继续使用原线程，还是新开线程；
2. 如何根据任务的性质、影响范围与风险等级，对每一轮开发任务做前置判断；
3. 在领导提出新增需求、或项目继续迭代时，如何用一套稳定的方法管理 Codex 的协作方式；
4. 如何减少 Codex 因旧上下文污染、任务混线、历史方案残留而导致的误改、乱改与高 token 消耗。

本方法论不是让使用者自行撰写完整 prompt，而是提供一套：

- 任务判断标准
- 线程管理规则
- 任务分级方法
- 本项目常见任务类型的处理原则

后续具体发给 Codex 的 prompt，仍建议由 GPT 在当前项目上下文中根据本轮任务现状定制输出。

---

## 二、总原则：Codex 的核心问题不是“会不会写代码”，而是“会不会在错误上下文里写代码”

在本项目实际开发过程中，Codex 的能力总体可用，但多次暴露出以下典型问题：

1. 会将历史失败方案误当成当前仓库现状；
2. 会把旧线程中的设计判断持续带入下一轮任务；
3. 会在任务边界不清时顺手扩展到无关模块；
4. 会在长线程中因上下文压缩而遗失关键前提，导致后续判断偏移；
5. 在项目已经发生回滚、重构、改路线后，若仍沿用旧线程，误改风险显著上升。

因此，Codex 使用的首要原则不是“尽量少开线程”，而是：

**确保每一轮开发发生在正确、干净、与当前仓库一致的上下文中。**

---

## 三、线程管理的第一性原则

### 1. 什么情况下优先继续同一线程

同一线程适用于：

- 当前任务仍属于同一个功能块的连续开发；
- 新改动强依赖上一轮刚确定的上下文；
- 当前线程中关于本功能的约束、字段名、交互规则仍然有效；
- 当前功能尚未完成验收，也尚未 `git push` 收口；
- 本轮只是上一轮的小修正、小补丁、小 bug 修复。

简单说：

**同一个功能还没做完，就继续同一线程。**

### 2. 什么情况下应优先新开线程

新开线程适用于：

- 上一轮功能已经验收通过并 `git push`；
- 当前开始的是一个新主题、新模块或新目标；
- 上一轮中出现过回滚、技术路线切换或失败方案撤销；
- 当前线程已经非常长，Codex 已经频繁压缩背景信息；
- 需要 Codex 基于“当前实际仓库状态”重新判断，而不是沿用历史方案；
- 当前任务跨模块、跨文件较多，且与旧线程主题不再高度一致；
- 当前要处理的是部署、平台迁移、文档整理、后台结构优化等全新方向。

简单说：

**一个稳定版本收口并 push 后，下一个功能默认应新开线程。**

## 四、任务分级方法：先判断任务是什么，再决定是否开新线程

后续所有 Codex 任务，建议先做以下三步判断：

### 第一步：判断任务性质

先判断这轮任务属于哪一类：

1. 小范围前端微调
2. 单模块功能开发
3. 跨模块功能开发
4. bug 修复
5. 部署与平台问题
6. 数据结构 / 提交链路调整
7. 文档与说明整理

### 第二步：判断任务影响范围

建议按影响范围分为三档：

#### A 级：单文件或单组件内改动
例如：
- 改按钮文案
- 改样式层级
- 改提示语
- 改单个组件的 UI 展示

特点：
- 影响范围小
- 风险低
- 容易局部验证

#### B 级：同一功能块内多文件协同改动
例如：
- 结果页表单 + `page.js` 状态管理
- 提交反馈逻辑 + 结果页组件 + 样式
- 答题页交互调整 + 页面状态联动

特点：
- 会改 2–3 个文件
- 涉及状态、交互、组件配合
- 中等风险

#### C 级：跨模块或跨链路改动
例如：
- 提交流程重构
- 联系方式写入策略变化
- 部署到新平台
- 数据表字段接入变化
- 结果页到后台查看链路联动

特点：
- 会改多个模块
- 容易受旧上下文污染
- 风险高

### 第三步：判断任务与当前线程关系

再问自己三个问题：

1. 这件事是不是上一轮功能的自然延续？
2. 当前线程中的设计前提是否仍然全部有效？
3. 如果让 Codex 继续沿用旧线程，会不会把历史失败方案再次带进来？

如果：
- 3 个问题里有 2 个以上回答“否”
- 或对第三个问题回答“会”

则建议：

**新开线程。**

## 五、面向本项目的具体判断规则

以下规则是专门针对“离婚力量表网页端”项目总结出来的。

### 规则 1：只要已经完成本地验收并 push，下一个功能默认新开线程

这是本项目最重要的一条规则。

原因：
- 本项目多次出现“上一轮已结束，但 Codex 仍沿用旧上下文”的情况；
- 只要已经形成稳定版本，新开线程通常比继续旧线程更省 token，也更稳。

### 规则 2：遇到以下任一情况，必须新开线程

- 代码已经回滚
- 技术路线已经切换
- 当前任务不再是上一轮同一功能
- 当前任务涉及部署平台变化
- 当前任务涉及 Supabase 提交策略变化
- 当前任务涉及 README / 项目文档 / 交接整理

### 规则 3：同一线程只适合承载“一个功能块的一条连续链路”

例如：
- 结果页 CTA 优化
- 页面内提交反馈
- 联系方式表单的一体化 insert

每一条都可以在一个线程里从：
- 方案确认
- 编码
- 修 bug
- 本地验收
- 收口

一路做完。

但不要让同一线程同时承担：
- 结果页优化
- README 更新
- 腾讯云部署
- 后台字段规范

这种混合任务。

### 规则 4：部署问题单独开线程

如：
- Vercel 问题
- 腾讯云 EdgeOne Pages 问题
- 大陆访问方案
- 域名 / 备案 / 环境变量部署问题

这些都不应和前台功能开发混在同一线程里。

### 规则 5：文档类任务默认单独开线程

如：
- README 更新
- 项目进展摘要
- 字段说明整理
- follow_up_status 使用规范

原因：
- 文档类任务不需要 Codex 再背负大量前端实现上下文；
- 单开线程更清爽，也更省上下文窗口。

## 六、如何按任务量和难度判断是否新开线程

### 一类任务：小任务

定义：
- 单文件内改动为主
- 目标非常明确
- 不改提交流程、不改数据结构、不改平台配置
- 本地验证成本低

例子：
- 改按钮文案
- 调整某条提示语
- 改一个输入框的必填规则
- 改一处布局层级

建议：
- 若属于当前功能收尾，可继续原线程；
- 若上一轮已 push，则新开线程也完全没问题。

### 二类任务：中任务

定义：
- 需要改 2–3 个文件
- 涉及组件 + 页面状态 + 样式联动
- 但不改变底层技术路线

例子：
- 结果页 CTA 优化
- 页面内 success/error 提示
- 留资表单并入同一次 insert

建议：
- 如果是上一轮功能的自然延续，可继续原线程；
- 如果上一轮已经收口并 push，建议新开线程。

### 三类任务：大任务

定义：
- 会影响提交流程、部署策略、数据库交互、产品路线
- 容易受旧上下文污染
- 需要先讨论方案，再进入编码

例子：
- 先提交结果再回写联系方式
- 调整 Supabase RLS / 提交方式
- 部署到腾讯云 EdgeOne Pages
- 新增后台页面或导出能力

建议：
- 必须新开线程；
- 先让 GPT 帮你梳理方案，再由 GPT 输出给 Codex 的任务指令；
- 不建议直接在旧线程里接着干。

## 七、本项目后续常见任务的线程建议

### 1. 前台交互微调
例如：
- 改结果页文案
- 改按钮顺序
- 改表单标签文字
- 调整输入框提示

判断：
- 若属于当前功能收尾，可继续同一线程；
- 若功能已 push，则新开线程。

### 2. 结果页转化优化
例如：
- 强化留资引导
- 优化提交成功后的承接文案
- 增加咨询说明模块

判断：
- 通常作为一个独立功能块，建议新开线程。

### 3. 数据提交策略改动
例如：
- 联系方式提交策略变化
- 想拿回 `id`
- 想从一次 insert 改成两步提交

判断：
- 必须新开线程；
- 必须先做方案讨论。

### 4. Supabase 字段与后台可读性优化
例如：
- `follow_up_status` 使用规范
- `admin_note` 如何填写
- `submission_source` 取值约定

判断：
- 新开线程；
- 属于后台与数据规范任务，不应与前台交互线程混用。

### 5. README / 文档更新
例如：
- README 同步
- 当前项目文档整理
- 当前阶段交接摘要更新

判断：
- 单独开线程；
- 通常先由 GPT 产出，再决定是否让 Codex同步写回仓库。

### 6. 新平台部署
例如：
- 腾讯云 EdgeOne Pages
- OSS / CDN
- 大陆访问测试镜像

判断：
- 单独开线程；
- 属于部署路线任务。

## 八、每轮任务开始前的前置判断方法

每一轮开发正式开始前，建议先问自己以下 6 个问题：

1. 这轮任务属于前台、后台、部署，还是文档？
2. 这轮任务是否仍然属于上一轮未完成的同一功能？
3. 上一轮是否已经完成验收并 push？
4. 这轮任务是否会改动数据提交方式或技术路线？
5. 当前线程里是否存在已经失效的历史方案？
6. 如果继续旧线程，Codex 是否可能把旧方案当成当前现状？

判断规则：

- 若第 2 题回答“是”，且第 3、4、5、6 题都回答“否”，可继续原线程；
- 其余大多数情况，建议新开线程。

## 九、给 Codex 布置任务时的最低必要信息

无论开新线程还是继续旧线程，给 Codex 下任务前都应明确以下四类信息：

### 1. 当前仓库基线
例如：
- 当前 GitHub main 已是最新稳定版本
- 或当前本地仓库已回滚到某一稳定版本

### 2. 本轮严格范围
例如：
- 只改 `app/page.js`、`components/ResultScreen.js`、`app/globals.css`
- 不改题目流程
- 不改计分逻辑
- 不改 Supabase schema

### 3. 本轮目标
例如：
- 增加结果页联系方式表单
- 优化提交按钮引导
- 更新 README

### 4. 本轮不要做什么
例如：
- 不要扩展到后台
- 不要顺手重构
- 不要沿用上一轮失败方案

本项目实际经验表明：

**Codex 是否稳定，往往取决于“不要做什么”有没有写清楚。**

## 十二、本项目当前稳定基线（供后续线程判断时参照）

以下内容用于帮助后续所有新对话快速判断：当前项目已经稳定实现到什么程度、哪些部分属于已通过验收的基线能力。

### 1. 当前前台稳定能力

当前稳定版本已实现并通过本地验收与 GitHub 同步的能力包括：

- Next.js 前台主流程稳定运行
- 两道系统分流题固定前置
- 普通计分题随机呈现
- 每题作答后自动进入下一题
- 保留“上一题”按钮
- 最后一题停留在“查看结果”状态
- 结果页页面内 success / error 提示
- 结果页 CTA 优化（主按钮优先提交）
- 联系方式表单直接嵌入结果页动作区
- `contact_name` 与 `contact_phone` 当前均为前端必填
- 测评结果与联系方式通过同一次 `insert` 一并写入 `assessment_results`
- 提交成功后按钮进入“已提交”状态，防重复提交逻辑已跑通

### 2. 当前数据与后台基线

当前已明确：

- Supabase 主表为 `assessment_results`
- 前台当前已接入并实际写入的联系方式字段为：
  - `contact_name`
  - `contact_phone`
- 当前表中也已预留：
  - `admin_note`
  - `follow_up_status`

但后两者当前仅作为后台管理预留字段，尚未纳入前台交互逻辑。

### 3. 当前部署基线

当前已明确：

- GitHub `main` 为当前稳定代码基线
- Vercel 线上版本可自动同步 GitHub 更新
- 腾讯云 EdgeOne Pages 已尝试部署，但默认 3 小时预览链接不适合作为长期大陆测试入口
- 大陆长期稳定访问方案尚未最终定稿

### 4. 当前方法论使用前提

后续所有新线程在参考本方法论时，都应默认以：

- 当前本地仓库实际状态
- GitHub `main` 当前稳定版本
- Supabase 实际表结构
- Vercel 线上当前版本

作为判断基线，而不是沿用旧线程中的历史失败方案。

## 十三、禁止直接交给 Codex 开始写代码的高风险任务类型

以下任务类型，不建议你直接打开 Codex 就让它开始改代码，而应先在 GPT 对话中完成方案判断，再由 GPT 输出约束清晰的 Codex 指令。

### 1. 提交流程改路线

例如：
- 从一次性 `insert` 改为两步提交
- 想在提交后拿回记录 `id`
- 想从前端提交改为后端接口提交

原因：
- 极易受旧上下文污染
- 极易影响现有稳定主链路
- 常常涉及 Supabase 权限或产品路线判断

### 2. Supabase 权限 / RLS / 返回值策略

例如：
- `insert(...).select("id")` 是否可用
- 是否允许前端读取刚写入的记录
- 是否需要调整策略让 update 生效

原因：
- 这已经不是单纯前端问题
- 若判断错误，容易让已跑通的主链路重新失败

### 3. 部署平台变化

例如：
- 从 Vercel 镜像部署到腾讯云
- 绑定大陆访问域名
- 配置 EdgeOne Pages
- 处理大陆访问、备案、默认域名时效问题

原因：
- 涉及平台机制而非单纯代码
- 容易把“代码问题”和“平台问题”混在一起

### 4. 数据结构扩展

例如：
- 新增留资字段
- 新增 leads 表
- 新增后台管理状态字段
- 新增结果导出结构

原因：
- 容易影响前台、后台、表结构和后续管理逻辑
- 不应在旧线程里顺手扩展

### 5. 后台管理能力开发

例如：
- 跟进状态管理页
- 导出功能
- 表格筛选
- 管理员备注编辑

原因：
- 与前台交互开发属于不同模块
- 不应混入前台线程

### 6. 涉及 4 个以上文件且跨模块的改动

判断经验：
- 只要一个新任务预计会同时改 `app/`、`components/`、`lib/`、数据库提交链路或部署配置，默认按高风险任务处理。

结论：

**以上任务类型一律先来 GPT 对话判断，不要直接让 Codex 自由发挥。**

## 十四、每轮开发的收口标准

为了避免“功能看起来差不多了，但其实还没真正完成”的情况，后续每轮开发建议统一按以下标准判断是否收口。

### 一轮任务只有同时满足以下条件，才视为真正完成

#### 1. 代码层面
- 本轮改动范围与预期一致
- 未扩展到无关模块
- 未保留明显残留逻辑

#### 2. 本地验证层面
- `npm run build` 通过，或明确确认失败仅由本地 `.next` 占用等环境问题造成
- 浏览器手工验收通过
- 关键用户链路已实际跑通

#### 3. 数据验证层面（如涉及 Supabase）
- 需确认后台表中已收到正确数据
- 需确认是写入同一条记录还是新建新记录
- 需确认字段值符合预期

#### 4. 版本管理层面
- 已执行 `git status`
- 已完成 `git add`
- 已完成 `git commit`
- 已完成 `git push`

#### 5. 线程管理层面
- 当前功能既然已经验收并 push，则下一个功能默认新开线程

### 不满足以上条件时，不建议草率进入下一轮功能开发

否则容易出现：
- 上一轮残留未清
- Git 收口不完整
- Codex 继续在脏上下文里工作
- 一个线程里混入多个半成品任务

---

## 十五、适用于本项目的推荐开发节奏

后续建议固定采用以下节奏：

### 阶段 1：先判断任务
在 GPT 对话中明确：
- 本轮任务是什么
- 任务属于哪一类
- 是否建议新开 Codex 线程
- 本轮不要动哪些内容

### 阶段 2：再让 Codex 先出最小改动方案
重点审查：
- 改哪些文件
- 改动范围是否过大
- 是否误用旧上下文
- 是否沿用了已经失效的历史方案

### 阶段 3：由 GPT 先审方案，再允许 Codex 动手

### 阶段 4：本地验证通过后立即 Git 收口

### 阶段 5：一个稳定版本收口后，下一个功能默认新开线程

这套节奏比“在一个长线程里不断叠加任务”更适合本项目。

---

## 十六、阶段性结论

对于“离婚力量表网页端”项目而言，Codex 不是不能用，而是必须：

- 控制任务边界
- 控制线程长度
- 控制历史上下文污染
- 在每轮任务前先做前置判断
- 在每轮任务后完成明确收口

本项目后续继续开发时，不应再用“一个超长线程一直做下去”的方式，而应采用：

**一个功能块一个线程，一个稳定版本一次收口。**

同时，应始终坚持：

**先让 GPT 判断，再让 Codex 动手；先确保上下文正确，再追求编码速度。**

这样既更省上下文窗口，也更容易控制误改风险，并能显著降低因历史方案残留带来的反复返工。
