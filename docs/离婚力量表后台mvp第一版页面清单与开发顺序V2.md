本文件用于在《离婚力量表后台 MVP 范围与数据口径草案 V1》与《离婚力量表后台 MVP 第一版字段清单 V1》的基础上，进一步明确：

- 后台 MVP 第一版实际已经完成哪些页面与能力；
- 每个页面的目标、信息结构与边界；
- 哪些能力已经从“预留”升级为“已实现”；
- 哪些能力仍不纳入当前后台 MVP；
- 后续交给 Codex 开发时应按什么顺序推进；
- 如何避免后台 MVP 第一版滑向复杂 CRM、完整客户门户或批量分析系统。

本文档为阶段更新版，重点补充以下最新事实：

1. 后台单条用户测评详细解读报告页已完成；
2. 网页端报告已改造为 A4 多页纸张式报告版式；

4. “导出报告”已改造为下拉菜单；

## 2. 当前阶段判断

当前项目已经完成公开前台主链路、结果页留资、动态雷达图、简洁版结果图导出、Supabase 写入、后台列表页、后台详情页、CSV 导出、单条详细报告页、报告图片导出与报告 PDF 导出。

后台第一版的目标仍不是建设完整后台系统，而是先让律所内部人员能够：

- 看见线索；
- 快速判断优先级；
- 记录当前跟进状态；
- 填写最小协作信息；
- 导出当前筛选结果；
- 查看单条用户测评详细解读报告；
- 将单条详细报告导出为 PNG 或 PDF 进行内部流转。

当前后台 MVP 第一版已经从“轻量线索管理 + 报告预留”升级为：

**线索管理 + 单条记录详情 + 后台字段编辑 + CSV 导出 + 单条详细报告预览 + PNG / PDF 报告导出。**

但仍需保持以下原则：

**少页面、强信息、轻操作、低耦合、便于快速上线试用。**

## 3. 页面范围总原则

### 3.1 第一版只做最小闭环

后台 MVP 第一版页面当前完成的闭环为：

**列表查看 → 筛选定位 → 进入详情 → 编辑核心字段 → 查看详细报告 → 导出 CSV / PNG / PDF → 内部流转。**

### 3.2 第一版不追求“像成熟 CRM”

第一版后台不追求：

- 仪表盘式经营分析；
- 复杂多角色权限；
- 自动消息提醒；
- 线索池与抢单机制；
- 多层级日志系统；
- 用户端个人门户；
- AI 大报告批量生成中心。

### 3.3 页面数量应继续控制

后台 MVP 第一版目前仍应控制为：

1. 后台列表页；
2. 单条记录详情页；
3. 单条用户详细报告页；
4. 导出能力：CSV、单条报告 PNG、单条报告 PDF；
5. 后续扩展模块：报告持久化、用户端授权、多人协作、操作日志。

其中，CSV 导出嵌入列表页，报告 PNG / PDF 导出嵌入单条详细报告页，不单独拆成导出中心。

## 4. 后台 MVP 第一版页面清单

## 4.1 页面一：后台记录列表页

### 页面定位

后台列表页是第一入口页，也是后台 MVP 第一版最重要的线索入口页面。

它的核心任务不是做复杂分析，而是让内部人员快速完成以下动作：

- 浏览最新线索；
- 判断优先级；
- 按条件筛选目标记录；
- 进入具体记录详情；
- 导出当前筛选结果。

### 页面目标

后台列表页必须完成：

1. 让用户快速看到有哪些新线索；
2. 让用户一眼分辨哪些记录值得优先处理；
3. 让用户能按常见业务条件筛选；
4. 让用户能快速点击进入详情；
5. 让用户能把当前筛选结果导出。

### 当前已实现能力

当前列表页已实现：

- 记录列表展示；
- 姓名、电话、微信、提交时间等基础信息展示；
- 结果等级、得分率等测评结果摘要展示；
- 子女 / 跨境分流信息展示；
- 当前跟进状态展示；
- 服务类型展示；
- 当前负责人展示；
- 最近更新时间展示；
- follow_up_status 筛选；
- 提交时间区间筛选；
- 结果等级筛选；
- 子女 / 跨境分流筛选；
- 姓名 / 电话关键词搜索；
- 当前筛选条件下 CSV 导出；
- 轻分页 / 展示增强；
- 点击进入单条详情页。

### 建议默认字段

列表页建议继续展示以下列：

- 提交时间；
- 姓名；
- 电话；
- 微信；
- 结果等级；
- 得分率；
- 子女分流结果；
- 跨境分流结果；
- 跟进状态；
- 服务类型；
- 当前负责人；
- 最近更新时间。

### 建议筛选项

第一版建议继续保留以下筛选：

- `follow_up_status`；
- 提交时间区间；
- `result_level`；
- `child_gate_answer`；
- `cross_border_gate_answer`；
- 是否留电话；
- 是否留微信；
- `assigned_to`；
- `service_type`。

### 建议搜索项

第一版建议继续支持关键词搜索：

- 姓名；
- 电话。

### 页面动作建议

列表页建议继续支持以下动作：

- 查看详情；
- 重置筛选；
- 导出当前筛选结果。

### 第一版不建议在列表页直接做的事情

不建议在列表页直接做：

- 大量行内编辑；
- 批量修改状态；
- 批量分配负责人；
- 批量生成报告；
- 复杂统计面板。

原因：这些能力会明显增加页面复杂度，不符合第一版“快速可用”的目标。

### 当前结论

列表页当前已经完成后台 MVP 第一版的核心线索入口能力。后续若继续开发列表页，应优先围绕正式使用反馈做小修，不应贸然扩展为完整 CRM 列表。

## 4.2 页面二：单条记录详情页

### 页面定位

详情页是后台 MVP 第一版的核心操作页。

它的任务不是把所有数据都平铺出来，而是让内部人员围绕一条记录完成：

- 看懂用户是谁；
- 看懂结果大概怎样；
- 看懂当前短板与分流情况；
- 填写当前跟进信息；
- 记录内部备注；
- 补充建联后的客户基础画像；
- 进入单条用户详细报告页。

### 页面目标

详情页必须完成：

1. 汇总展示该用户的基础信息；
2. 汇总展示该用户的测评结果；
3. 允许编辑后台核心管理字段；
4. 展示原始作答与维度明细；
5. 支持建联后人工补充客户画像与核心争议摘要；
6. 提供进入单条详细报告页的入口。

### 当前已实现能力

当前详情页已实现：

- 基础联系方式展示；
- 提交来源与提交时间展示；
- 结果等级、得分率、总分 / 动态满分展示；
- 短板维度展示；
- 子女 / 跨境分流结果展示；
- 各维度均分展示；
- 原始答案展示；
- 后台跟进字段编辑；
- 内部备注编辑；
- 建联补充信息编辑；
- 保存当前编辑；
- 返回列表；
- 进入详细报告页。

### 详情页当前模块结构

#### 模块一：基础信息

展示：

- 姓名；
- 电话；
- 微信；
- 提交时间；
- 来源。

#### 模块二：测评结果摘要

展示：

- 结果等级；
- 得分率；
- 总分 / 动态满分；
- 当前短板维度；
- 子女分流结果；
- 跨境分流结果。

#### 模块三：维度详情

展示：

- 各维度平均分；
- 必要维度解释；
- 原始答案。

#### 模块四：后台跟进信息

展示并可编辑：

- 跟进状态；
- 服务类型；
- 当前负责人；
- 约面人员；
- 约面时间；
- 最近跟进时间；
- 最近修改人；
- 最近更新时间。

#### 模块五：内部备注

展示并编辑：

- `admin_note`。

#### 模块六：建联补充信息

展示并编辑：

- `client_age`；
- `client_gender`；
- `client_location`；
- `asset_tier_level`；
- `marital_dispute_summary`。

#### 模块七：详细报告入口

当前详情页可进入：

- `/leads/[id]/report`

用于查看单条用户测评结果详细解读报告。

### 页面动作建议

详情页建议继续支持以下动作：

- 保存当前编辑；
- 返回列表；
- 进入详细报告页。

### 第一版详情页不建议做的事情

不建议第一版详情页直接做：

- 多人协作评论流；
- 历史版本比对；
- 复杂审批流；
- 用户授权查看管理中心；
- 自动生成长篇 AI 报告；
- 报告定稿流程。

### 当前结论

详情页已经完成单条线索最小管理面板的核心功能。后续重点不是继续堆功能，而是根据真实使用反馈判断是否需要多人协作、保存冲突提示和操作日志。

## 4.3 页面三：单条用户详细报告页

### 页面定位

单条用户详细报告页是后台 MVP 第一版中已经完成的重要扩展页面。

它用于将用户测评结果从详情页摘要，进一步生成可阅读、可审阅、可导出的完整内部报告。

当前该页面是：

**单条用户测评结果详细解读报告页。**

它不是：

- 批量用户画像报告；
- 内容创作赋能报告；
- 用户端报告中心；
- AI 自动深度报告系统；
- 报告审核定稿系统。

### 页面目标

单条详细报告页当前承担以下任务：

1. 完整展示用户总结果说明；
2. 完整展示各维度功能说明；
3. 完整展示各维度结果解析；
4. 完整展示各维度提升建议；
5. 提供网页端 A4 报告预览；
6. 提供移动端长图报告预览；
7. 支持导出报告图片 PNG；
8. 支持导出报告 PDF；
9. 便于内部审阅、保存、发送与沟通使用。

### 当前已实现能力

当前详细报告页已实现：

- `/leads/[id]/report` 路由；
- 后台鉴权保护；
- 报告基础信息区；
- 报告状态提示；
- 网页端 A4 报告预览；
- 移动端 750px 单列长图报告预览；
- “预览报告”下拉菜单；
- “导出报告”下拉菜单；
- 导出图片 PNG；
- 导出 PDF；
- A4 报告在移动端预览状态下离屏挂载，以支持 PDF 导出；
- 网页端 PNG 导出当前 A4 报告；
- 移动端 PNG 导出当前移动端长图；
- PDF 导出固定基于 A4 网页端报告；
- PDF 导出不使用浏览器打印；
- PDF 导出不弹浏览器打印面板；
- PDF 导出基于 A4 页面逐页生成。

### 当前报告文案来源

报告文案统一来自：

- 《离婚力测量量表解读文案主档 V2》

后台详细报告可使用：

- 总分评估结果；
- 维度功能说明；
- 维度结果解析；
- 维度提升建议。

当前不应在报告页中另行硬编码或重写核心文案。

## 4.4 网页端 A4 报告版式

### 版式定位

网页端报告已经从原先单个长画布 / 海报式报告，调整为 A4 多页纸张式报告。

该版式用于：

- 后台电脑端预览；
- 内部审阅；
- PDF 导出基础；
- 后续可能的 A4 图片导出基础。

### 当前结构

A4 报告由多张独立纸页组成，页面结构包括：

1. 封面 / 核心摘要页；
2. 总体评价与维度概览页；
3. 各维度详细解读页；
4. 报告使用边界与品牌页脚页。

每页使用独立 A4 页面 DOM，便于后续：

- 逐页截图；
- 逐页写入 PDF；
- 控制页面边界；
- 避免长图裁切导致文字断裂。

### 视觉要求

当前 A4 报告应保持：

- A4 纵向纸张比例；
- 多页纸张结构；
- 页面居中；
- 宽屏左右留白；
- 白底纸张；
- 克制阴影；
- 明确页边距；
- 品牌深蓝体系；
- Logo、水印、图标与页脚；
- 更像正式咨询报告 / 律所报告，而不是手机长截图。

### 当前结论

网页端 A4 报告已经成为后续 PDF 导出的基础版式。后续 PDF 相关优化，应优先在 A4 版式层面做局部优化，而不是另做第三套 PDF 专用文案或报告结构。

## 4.6 导出能力

### 4.6.1 CSV 导出

CSV 导出仍作为列表页附属能力存在。

当前定位：

- 导出当前筛选结果；
- 用于内部流转、人工查看与进一步处理；
- 不作为独立导出中心。

当前建议导出字段继续包括：

- 提交时间；
- 姓名；
- 电话；
- 微信；
- 结果等级；
- 得分率；
- 子女分流结果；
- 跨境分流结果；
- 当前短板维度；
- 跟进状态；
- 服务类型；
- 当前负责人；
- 约面人员；
- 约面时间；
- 最近跟进时间；
- 最近更新时间；
- 最近修改人；
- 内部备注。

第一版不建议默认导出：

- 原始答案 JSON；
- 复杂维度嵌套结构；
- 用户可见详细报告全文；
- 内部尚未定稿的分析长文。

### 4.6.2 报告 PNG 导出

报告 PNG 导出嵌入单条详细报告页。

当前规则：

- 网页端预览状态：导出 A4 网页端报告 PNG；
- 移动端预览状态：导出移动端长图 PNG；
- 使用 `html-to-image` / `toPng`；
- 按当前 `previewMode` 选择导出节点；
- 不涉及服务端生成；
- 不写入数据库；
- 不保存文件到云存储。

### 4.6.3 报告 PDF 导出

报告 PDF 导出嵌入单条详细报告页。

当前规则：

- PDF 固定基于 A4 网页端报告生成；
- 即使当前是移动端预览，也导出 A4 PDF；
- 使用 `html-to-image` 将 A4 页面转为图片；
- 使用 `jspdf` 写入 PDF；
- 按 `.a4-report-page` 逐页生成；
- 直接下载 `.pdf` 文件；
- 不使用 `window.print`；
- 不使用 `@media print`；
- 不弹浏览器打印面板；
- 不依赖用户手动选择“保存为 PDF”；
- 不涉及服务端 PDF；
- 不涉及报告持久化。

### 4.6.4 “导出报告”交互

当前“导出报告”已改为下拉菜单。

菜单项包括：

1. 导出图片 PNG；
2. 导出 PDF。

当前交互规则：

- 用户选择“导出图片 PNG”时，沿用当前预览版本导出图片；
- 用户选择“导出 PDF”时，固定导出 A4 网页端报告 PDF；
- 导出过程中禁用重复点击；
- 导出状态区分图片导出与 PDF 导出。

## 5. 第一版明确不做的页面

为防止后台 MVP 失控，第一版仍明确不做以下页面。

- 转化率面板；
- 服务类型占比图；
- 短板维度热度图；
- 人员绩效分布图。

### 5.2 批量操作页

暂不做：

- 批量分配；
- 批量改状态；
- 批量导出模板配置；

### 优先级 1：同步更新后台相关底座文档

- 正式部署上线路径建议；
- 页面信息架构与文案边界文档。

### 优先级 2：正式国内部署准备

下一步建议进入正式部署准备：

- 确认正式前台域名；
- 确认正式后台域名；
- 确认备案与 DNS 权限；
- 验证 EdgeOne 中国大陆 / 全球含大陆可用区；
- 准备正式部署验收清单；
- 若 EdgeOne 大陆区不满足后台需求，预备中国大陆云服务器方案。

### 优先级 3：后台多人使用最小升级预研

若准备给更多同事使用后台，建议预研：

- 多账号登录；
- 真实 `updated_by`；
- 操作日志；
- 保存冲突提示；
- 基础角色权限；
- 报告导出权限控制。

### 优先级 4：报告持久化与版本化预研

若业务需要报告可追溯、可审核、可定稿，应预研：

- `assessment_reports` 表；
- `report_content` JSON；
- `report_generated_at` 真正启用；
- PDF 文件是否保存；
- 报告审核状态；
- 用户端开放前置条件。

### 优先级 5：依赖安全检查与维护

后续单独处理：

- `npm audit` finding；
- `jspdf` 与相关依赖安全风险；
- 是否可小版本升级；
- 升级后报告导出回归。

## 9. 给后续 Codex 开发的注意事项

后续涉及后台页面开发时，应继续遵守：

1. 一个功能完成验收并 push 后，下一个功能默认新开 Codex 线程；
2. 涉及部署、鉴权、数据结构、报告持久化、多账号系统的任务必须新开线程；
3. 每轮任务先由 GPT 明确范围，再给 Codex 下指令；
4. 不要让 Codex 在长线程中继承失效历史方案；
5. 不要让报告任务混入批量画像、内容赋能或用户端报告开放。
