# 离婚力量表后台 MVP 范围与数据口径草案（阶段更新版｜A4 报告与 PDF 导出后）

## 1. 文档目的

本草案用于在“离婚力量表网页端”后续开发继续推进前，统一当前后台 MVP 的：

- 目标与边界；
- 功能范围；
- 数据口径；
- 字段设计原则；
- 状态流转规则；
- 报告输出能力边界；
- 暂不纳入 MVP 的事项。

本文档为阶段更新版，重点补充以下最新事实：

1. 后台 MVP 已不再停留于“详细报告预留区”阶段；
2. 单条用户测评结果详细解读报告页已经完成；
3. 网页端报告已改造为 A4 多页纸张式报告；
4. 移动端 750px 单列长图报告继续保留；
5. 单条报告支持 PNG 导出；
6. 单条报告支持真正 PDF 文件导出；
7. PDF 导出为前端生成，基于 A4 页面逐页生成，不使用浏览器打印；
8. 当前仍未做 `report_content` 持久化、报告审核定稿、用户端授权查看、批量报告或完整 CRM。

本文档不是最终技术方案，也不是数据库迁移脚本，而是用于统一后台 MVP 的产品范围和数据语言，避免后续开发滑向完整 CRM、客户门户、报告归档系统或批量数据分析平台。

## 3. 后台 MVP 的核心目标

后台 MVP 当前只解决以下问题。

### 3.1 让律所内部能接住量表产生的线索

用户完成量表并提交信息后，后台应能够让法律顾问、律师或相关协作人员快速看到：

- 这是谁；
- 联系方式是什么；
- 测评结果大概如何；
- 当前是否已经有人跟进；
- 跟进到什么阶段；
- 下一步应由谁继续处理。

### 3.2 让后台记录从“静态收表”变成“可管理线索”

后台 MVP 的重点不是复杂分析，而是把当前 `assessment_results` 从单纯结果记录表，升级为可用于内部跟进和导出的基础线索主表。

当前已经实现：

- 线索列表查看；
- 条件筛选；
- 关键词搜索；
- 单条详情查看；
- 后台字段编辑；
- 建联补充信息维护；
- CSV 导出；
- 单条详细报告查看与导出。

### 3.3 让单条详细报告成为内部沟通辅助工具

当前后台已经完成单条用户测评结果详细解读报告页。

该报告当前用于：

- 内部审阅；
- 律师或助理理解用户测评结构；
- 咨询前准备；
- 与内部同事流转；
- 必要时导出 PNG 或 PDF 作为沟通辅助材料。

当前报告不是：

- 用户端自动开放报告；
- 律师审核定稿后的正式法律意见书；
- 自动生成的 AI 深度报告；
- 批量用户画像分析报告；
- 内容选题 / SEO / GEO 数据分析报告。

### 3.4 为后续报告持久化、用户授权查看与多人协作预留扩展位

“报告内容持久化”“律师审核定稿”“授权用户查看详细结果”“多人账号与操作日志”是后续重要方向，但不应在后台 MVP 当前阶段强行扩成完整系统。

MVP 阶段应继续保留字段与路径，但不直接扩展为完整客户门户、报告审核系统或 CRM。

## 4. MVP 阶段明确纳入范围的功能

## 4.1 后台记录列表页

后台列表页至少支持：

- 查看客户记录列表；
- 查看姓名、电话、微信、提交时间；
- 查看结果等级、得分率；
- 查看子女 / 跨境分流情况；
- 查看当前跟进状态；
- 查看当前负责人员；
- 查看服务类型；
- 查看最近更新时间；
- 按条件筛选；
- 按关键词搜索；
- 进入详情页；
- 导出当前筛选结果 CSV。

当前已实现：

- 列表展示；
- 筛选；
- 时间区间筛选；
- 搜索；
- 轻分页；
- CSV 导出；
- 进入详情。

## 4.2 列表筛选与搜索

后台 MVP 第一版建议支持并当前已基本实现以下筛选：

- 按 `follow_up_status` 筛选；
- 按提交时间区间筛选；
- 按结果等级筛选；

- 按服务类型筛选。

后续如有真实使用反馈，可继续小步增强筛选，但不建议直接扩展为复杂数据仪表盘。

## 4.3 单条记录详情页

详情页支持查看：

- 测评总结果；

详情页当前支持编辑：

- `admin_note`；
- `service_type`；
- `assigned_to`；
- `appointment_owner`；
- `appointment_time`；
- `client_age`；
- `client_gender`；
- `client_location`；

详情页当前不承担：

- 多人协作评论流；
- 操作日志查看；
- 保存冲突检测；
- 报告审核定稿；
- 用户授权查看管理。

## 4.4 单条用户详细报告页

后台 MVP 当前已经纳入并实现单条用户详细报告页。

详细报告页支持：

- 查看单条用户测评详细解读报告；
- A4 网页端报告预览；
- 移动端长图报告预览；
- 预览模式切换；
- 导出图片 PNG；
- 导出 PDF。

报告内容包括：

- 报告头部；
- 用户称呼；
- 报告生成时间；
- 结果等级；
- 得分率；
- 核心结论摘要；
- 总体评价；
- 关键指标；
- 纳入报告维度；
- 动态雷达图；
- 维度结构概览；
- 七维度详细解读；
- 报告使用边界；
- 律所品牌页脚。

报告文案来源：

- 《离婚力测量量表解读文案主档 V2》

报告当前不做：

- `report_content` 持久化；
- 报告审核定稿；
- 报告版本快照；
- 用户端授权查看；
- 报告文件上传或云端存储；
- 批量报告生成。

## 4.5 报告 PNG 导出能力

当前报告 PNG 导出为前端本地生成。

导出规则：

- 当前预览为网页端 A4 报告时，导出 A4 网页端报告 PNG；
- 当前预览为移动端长图报告时，导出移动端长图 PNG；
- 使用 `html-to-image` / `toPng`；
- 不走服务端；
- 不写入数据库；
- 不保存到云存储。

PNG 导出定位：

- 内部快速保存；
- 图片化流转；
- 微信或聊天工具沟通辅助；
- 与 PDF 导出并存。

## 4.6 报告 PDF 导出能力

当前报告 PDF 导出已经纳入后台 MVP，并已实现。

PDF 导出规则：

- 固定基于 A4 网页端报告生成；
- 即使当前预览为移动端长图，导出的 PDF 仍为 A4 报告；
- 基于 `.a4-report-page` 逐页生成；
- 使用 `html-to-image` 将每页转为图片；
- 使用 `jspdf` 写入 PDF；
- 直接下载 `.pdf` 文件；
- 不使用浏览器打印；
- 不弹出浏览器打印面板；
- 不依赖用户手动选择“保存为 PDF”；
- 不使用服务端 PDF；
- 不使用 Puppeteer / Playwright。

PDF 导出定位：

- 内部审阅；
- 正式感更强的流转材料；
- 便于保存、归档和发送；
- 当前仍不等同于经律师审核定稿的正式法律意见文件。

## 4.7 最小权限控制

后台 MVP 第一版至少应要求：

- 仅内部授权人员可访问后台；
- 不允许匿名访问；
- 不允许前台用户直接访问后台页面。

当前已实现：

- 最小后台登录；
- 未登录访问拦截；
- HttpOnly Cookie 相关会话机制；
- 页面 / Route Handler / Server Action 层鉴权；
- EdgeOne 海外区线上登录与未登录回跳验收正常。

当前尚未实现：

- 多账号登录；
- 角色权限；
- 字段级权限；
- 真实 `updated_by`；
- 操作日志；
- 报告导出权限控制。

## 5. MVP 阶段明确不纳入范围的功能

以下内容仍不建议纳入后台 MVP 当前阶段。

## 5.1 完整 CRM 系统

暂不做：

- 客户多阶段商机漏斗系统；
- 自动提醒 / 自动分配；
- 复杂协作日志；
- 多维绩效统计；
- 全流程案件管理；
- 客户生命周期管理。

## 5.2 完整客户门户

暂不做：

- 用户登录后查看全部历史记录；
- 用户自行编辑个人信息；
- 用户在线与律师持续互动；
- 用户端复杂授权中心；
- 用户端下载详细报告；
- 用户端查看 PDF 报告历史版本。

## 5.3 AI 自动深度报告系统

暂不做：

- 对每个客户实时大模型生成长报告；
- 后台自动批量生成高成本个性化报告；
- 未经律师确认即向用户开放完整分析；
- AI 自动改写律师意见；
- AI 生成正式法律判断。

## 5.4 复杂角色权限系统

暂不做：

- 按团队、部门、律师级别做复杂权限树；
- 字段级权限；
- 组织架构级可见性控制；
- 报告导出审批流。

## 5.5 报告持久化与审核定稿系统

当前暂不做：

- `report_content` 持久化；
- 报告内容快照；
- 报告审核状态；
- 律师定稿流程；
- 报告版本比对；
- 报告文件云存储；
- 用户端授权查看。

说明：

当前 PDF / PNG 导出是基于实时报告页面生成的前端导出能力，不等于报告内容已经被持久化、审核或定稿。

## 5.6 批量用户画像 / 统计 / 内容赋能分析报告

当前暂不做：

- 批量用户画像报告；
- 线索质量统计；
- 维度热度统计；
- 服务类型转化分析；
- 面向内容创作、SEO / GEO 的批量洞察报告；
- 批量 PDF 生成。

说明：

当前已经完成的是“单条用户测评结果详细解读报告”，不得与批量分析报告混淆。

## 6. 后台 MVP 建议采用的数据结构策略

## 6.1 总体原则

后台 MVP 应继续遵循：

- 在现有 `assessment_results` 基础上尽量小步扩展；
- 避免第一阶段就拆成大量表；
- 先保证线索可查看、可编辑、可导出；
- 对未来详细报告持久化、服务协同、授权查看预留扩展位；
- 当前 PDF / PNG 导出不要求新增数据库字段。

## 6.2 当前已采用方案

当前仍以 `assessment_results` 作为线索主表。

原因：

- 当前前台提交已经稳定写入该表；
- 线索、结果、联系方式当前天然属于同一条记录；
- 先扩表比先重构更适合 MVP；
- 可显著降低迁移成本与开发复杂度；
- 后台当前已经基于该主表完成列表、详情、报告页面。

## 6.3 PDF / PNG 导出与数据结构关系

当前报告导出能力不新增数据库字段。

原因：

- PNG / PDF 导出均为前端即时生成；
- 当前不保存导出文件；
- 当前不保存报告内容快照；
- 当前不记录每次导出行为；
- 当前不区分报告审核版本；
- 当前不开放用户端查看。

因此，当前不需要新增：

- `assessment_reports` 表；
- `report_content` 字段；
- PDF 文件 URL 字段；
- 报告导出日志表；
- 报告审核状态字段。

## 6.4 第二阶段再考虑的扩展方向

若后续后台使用频率明显上升，再考虑新增：

- `assessment_followup_logs`：跟进日志表；
- `assessment_reports`：详细报告快照 / 版本表；
- `staff_profiles`：内部人员映射表；
- `service_orders`：服务转化表；
- `report_export_logs`：报告导出日志；
- `report_files`：报告文件存储记录。

这些都不作为当前 MVP 必做项。

1. 前台测评结果字段；

3. 后台跟进字段；

## 7.1 前台测评结果字段

以下字段继续沿用现有口径：

- `id`；
- `created_at`；
- `total_score`；
- `dynamic_full_score`；
- `score_rate`；
- `result_level`；

- `child_gate_answer`；
- `cross_border_gate_answer`；

这些字段原则上由前台写入，后台只读，不建议在后台人工修改。

### 7.1.1 `dimension_scores`

`dimension_scores` 当前已经由前台正式写入新提交记录。

字段意义：

- 存储各维度平均分；
- 用于后台详情页展示；
- 用于单条详细报告；

注意：

## 7.2 用户留资字段

继续沿用：

- `contact_name`；
- `contact_phone`；
- `contact_wechat`。

这些字段主要来源于前台提交。

后台如确需修改，应谨慎，只作为纠错用途，不应频繁手工改写原始留资内容。

---

## 7.3 后台跟进字段

当前建议并已使用以下字段：

- `follow_up_status`；
- `admin_note`；
- `service_type`；
- `assigned_to`；
- `appointment_owner`；
- `appointment_time`；
- `last_follow_up_at`；
- `updated_by`；
- `updated_at`。

### 7.3.1 `follow_up_status`

字段含义：当前线索所处的跟进阶段。

建议类型：字符串枚举。

建议第一版枚举值：

- `new`：新提交，未处理；
- `to_follow`：已查看，待联系；
- `contacted`：已联系，待回复 / 待进一步确认；
- `consulting`：已进入有效沟通或正式咨询安排中；
- `converted`：已转化为明确服务；
- `invalid`：无效线索 / 重复 / 无法联系 / 明确无意向。

建议规则：

- 前台插入新记录时默认值为 `new`；
- 后台编辑时必须从枚举中选择；
- 不允许自由输入文本替代状态。

### 7.3.2 `admin_note`

字段含义：当前线索的内部补充说明与处理备注。

建议用途：

- 记录沟通结论；
- 记录风险点；
- 记录用户当前诉求；
- 记录下一步安排。

建议填写原则：

- 只写客观事实与处理信息；
- 不写情绪化评价；
- 不写与业务无关的私密内容；
- 不在其中替代状态字段；
- 不在其中替代服务类型字段；
- 不把完整案情长文全部堆入该字段。

建议模板：

`[日期 处理人] 本次沟通情况；用户当前核心诉求；当前判断；下一步安排。`

### 7.3.3 `service_type`

字段含义：律所当前拟提供、正在提供或已进入的服务类型。

建议类型：文本数组。

建议第一版枚举值：

- `none`：尚未进入明确服务；
- `single_consultation`：单次咨询；
- `divorce_escorting`：离婚陪跑；
- `long_term_consultation`：长期咨询；
- `screening_service`：甄选服务；
- `litigation_representation`：诉讼代理；
- `agreement_support`：协议离婚协助；
- `cross_border_support`：跨境婚姻 / 跨境身份专项支持；
- `other`：其他。

建议规则：

- 第一版按多选设计；
- 尚未明确服务方向，可标记 `none`；
- 可按实际情况组合多个服务类型；
- 不应把该字段理解为最终收费字段或订单字段。

### 7.3.4 `assigned_to`

字段含义：当前主要负责该线索的内部人员。

第一版建议：

- 先允许写人员姓名或统一内部称呼；
- 不必一开始就强绑定用户表；
- 后续如后台使用稳定，再升级为人员 ID 关联。

### 7.3.5 `appointment_owner`

字段含义：当前负责约面、约通话、推进下一步沟通的人。

说明：

- 该字段与 `assigned_to` 可以一致，也可以不同；
- 第一版保留独立字段，避免一个字段承担所有责任人含义。

### 7.3.6 `appointment_time`

字段含义：当前已确认的下一次正式沟通时间。

说明：

- 若尚未约定，则为空。

### 7.3.7 `last_follow_up_at`

字段含义：最近一次人工跟进时间。

建议规则：

- 后台更新状态或备注时同步更新；
- 第一版可由保存动作自动维护；
- 不建议人工自由改。

### 7.3.8 `updated_by`

字段含义：最近一次修改后台信息的内部人员。

当前边界：

- 第一版仍为弱记录；
- 当前尚未实现多账号体系，因此无法可靠记录真实内部人员；
- 后续多账号登录实现后，应升级为真实人员身份。

## 8. follow_up_status 的状态流转建议

后台 MVP 第一版建议继续采用轻量状态流，而不是复杂漏斗系统。

建议流转如下：

`new → to_follow → contacted → consulting → converted`

并允许任一阶段进入：

`invalid`

### 8.1 各状态定义

#### new

定义：前台新提交，后台尚无人处理。

进入条件：新记录默认进入。

#### to_follow

定义：内部已看到这条记录，认为值得继续联系，但尚未完成有效联系。

适用场景：

- 已分配负责人；
- 待电话 / 微信联系；
- 等待合适时间触达。

#### contacted

定义：已发起联系，已建立初步沟通，但尚未进入稳定咨询推进。

适用场景：

- 已电话 / 微信联系；
- 用户仍在考虑；
- 待用户回复；
- 待补充资料。

#### consulting

定义：已进入明确的进一步沟通或服务判断阶段。

适用场景：

- 已约正式咨询；
- 已进行较深入沟通；
- 正在判断服务方案。

#### converted

定义：已形成明确服务承接。

适用场景：

- 已购买咨询；
- 已签约服务；
- 已进入正式案件推进。

#### invalid

定义：该记录不再作为有效线索继续推进。

适用场景：

- 明确无意向；
- 无法联系；
- 重复提交；
- 明显无效信息；
- 非目标客群。

### 8.2 状态使用规则

建议遵循：

- 一个线索同一时点只能有一个主状态；
- 备注记录具体过程，状态反映当前阶段；
- 不使用自由文本状态；
- 不额外再造若干近义状态，防止后期无法筛选统计。

## 9. admin_note 的填写口径建议

## 9.1 目标

`admin_note` 不是聊天记录备份，也不是案情全文记录，而是内部协作所需的“当前判断与下一步信息”。

## 9.2 建议记录内容

建议优先记录：

- 当前核心诉求；
- 已完成的联系动作；
- 用户当前态度与阶段；
- 当前主要风险点；
- 下一步动作；
- 需要谁接手。

## 9.3 不建议记录的内容

不建议写入：

- 与业务无关的主观评价；
- 侮辱性、情绪化表达；
- 不必要的个人隐私；
- 与字段重复的内容；
- 不能核实的法律判断；
- 完整聊天记录全文；
- 替代正式案情笔记的大段材料。

## 9.4 推荐写法

建议采用固定结构：

`[日期 处理人] 已做动作；用户当前情况；关键判断；下一步。`

示例：

`[2026-04-17 Sandra] 已电话沟通。用户当前主要关注财产分割与孩子抚养安排，倾向先做一次正式咨询；下一步为下周确认面谈时间。`

## 9.5 后续升级方向

若后台使用频率提高，后续应考虑将 `admin_note` 从单一文本升级为独立跟进日志表。

但在 MVP 阶段，先用单字段承载最小协作信息即可。

## 10. 服务类型字段的口径建议

## 10.1 目标

`service_type` 用于回答：

“这条线索目前在律所内部被判断为更接近哪些服务承接方向？”

它不是最终收费字段，也不是正式订单系统字段。

## 10.2 当前业务口径理解

结合现有客户分流规则，服务类型应理解为：

- 短期服务可包含单次咨询；
- 长期服务中，离婚陪跑与长期咨询是两种不同服务，不应混同；
- 对高净值、高复杂度客户，可在主服务之外叠加甄选服务；
- 跨境婚姻或身份风险可作为专项支持方向；
- 诉讼代理与协议支持可作为更明确的法律服务承接方向。

因此 `service_type` 更适合按多选设计，而不是互斥单选。

## 10.3 第一版建议值

建议采用多选：

- `none`；
- `single_consultation`；
- `divorce_escorting`；
- `long_term_consultation`；
- `screening_service`；
- `litigation_representation`；
- `agreement_support`；
- `cross_border_support`；
- `other`。

## 10.4 使用原则

- 尚未明确前，用 `none`；
- 若当前仅进入一次性短期承接，可标记 `single_consultation`；
- 若客户具备较好的离婚意愿与推进能力，且需要持续承接和推进，可标记 `divorce_escorting`；
- 若客户短期内不一定立即离婚，或当前更需要持续认知、准备与判断支持，可标记 `long_term_consultation`；
- 若客户为高净值、高复杂度客群，需要额外专业资源筛选、匹配和协调，可叠加 `screening_service`；
- 若进入诉讼代理方向，可标记 `litigation_representation`；
- 若进入协议离婚支持方向，可标记 `agreement_support`；
- 若涉及跨境婚姻 / 跨境身份问题，可标记 `cross_border_support`；
- 第一版即应支持组合型服务；
- 若后续需要更细的统计、结算或流程联动，再升级为关联结构。

## 10.5 推荐存储格式

当前建议继续使用：

- Postgres `text[]`

优点：

- 贴合多选；
- 查询相对直接；
- 不需要第一版就引入关联表；
- 页面展示可映射中文名称。

## 11. 报告输出能力的数据边界

## 11.1 当前报告生成方式

当前详细报告是基于：

- 当前 `assessment_results` 记录；
- 当前 `dimension_scores`；
- 当前 `answers` / fallback 计算；
- 当前报告内容配置；
- 当前《离婚力测量量表解读文案主档 V2》；
- 当前前端报告组件；

实时生成的后台报告页面。

## 11.2 PNG 导出边界

PNG 导出是前端即时导出能力。

它不代表：

- 报告已归档；
- 报告已审核；
- 报告已定稿；
- 报告内容已持久化；
- 报告已开放给用户。

## 11.3 PDF 导出边界

PDF 导出同样是前端即时导出能力。

它不代表：

- 系统已保存 PDF 文件；
- 系统已记录导出历史；
- 报告内容已冻结；
- 律师已审核该报告；
- 用户可直接访问该报告。

## 11.4 后续如需归档需新增能力

如果业务上需要“报告可追溯、可审核、可定稿、可对用户开放”，则后续应单独设计：

- 报告内容快照；
- 报告版本号；
- 报告生成时间；
- 报告审核状态；
- PDF 文件存储位置；
- 用户可见性；
- 报告导出日志。

该方向应作为“报告持久化与版本化”专项任务处理，不应混入当前 MVP 导出能力。

## 12. 当前安全与权限边界

当前后台使用最小鉴权，适合：

- 项目负责人；
- 开发者验收；
- 小范围内部测试；
- 临时演示。

当前不适合未经培训的大范围长期多人使用。

主要风险：

- 多人共用同一套账号密码；
- 无真实人员身份；
- 无操作日志；
- 无字段级权限；
- 无导出权限控制；
- 多人同时编辑同一条记录可能出现覆盖。

后续多人使用前，建议先预研：

- 多账号登录；
- 真实 `updated_by`；
- 操作日志；
- 保存冲突提示；
- 基础角色权限；
- 报告导出权限控制。

## 13. 当前部署边界

当前后台已部署在腾讯云 EdgeOne Pages 海外可用区，并完成线上回归验收。

当前部署可用作：

- 开发者线上验收环境；
- 临时演示环境；
- 技术验证环境。

当前部署不应作为：

- 正式上线环境；
- 大范围内部试用环境；
- 面向中国大陆长期稳定访问的后台入口。

原因：

- 当前 EdgeOne 区域为全球可用区（不含中国大陆）；
- 中国大陆访问不稳定；
- 部分人员可能需要 VPN；
- 不满足正式上线的中国大陆稳定访问要求。

正式部署仍应优先考虑：

1. 已备案域名子域名 + EdgeOne 中国大陆 / 全球含大陆可用区；
2. 已备案域名子域名 + 中国大陆云服务器部署。

正式部署前必须回归：

- 登录；
- 列表；
- 筛选；
- CSV 导出；
- 详情页保存；
- A4 报告预览；
- 移动端报告预览；
- PNG 导出；
- PDF 导出；
- 静态资源加载；
- 未登录拦截；
- 退出登录。

## 15. 当前一句话结论

后台 MVP 当前已经完成从“线索查看与跟进”到“单条详细报告预览与 PNG / PDF 导出”的阶段性闭环；当前数据结构仍以 `assessment_results` 为线索主表，报告导出为前端即时生成，不新增报告持久化字段或报告表。下一阶段应优先推进正式国内部署准备、多人协作最小升级预研与报告持久化 / 版本化预研，而不是继续扩大当前 MVP 的页面数量。
