# 配偶高自恋特质量表后台与数据库适配方案 V1

## 1. 文档用途

本文档用于在“配偶高自恋特质与高冲突婚姻风险自测量表”进入 VS Code + Codex 开发前，统一第一阶段后台与数据库适配方案。

本文档承接以下底座文件：

1. 《配偶高自恋特质量表网页端产品与开发方案 V1》；
2. 《配偶高自恋特质量表题目-维度-计分映射表 V1》；
3. 《配偶高自恋特质量表结果分级规则与结果页文案框架 V1》；
4. 《配偶高自恋特质量表网页信息架构与页面文案草案 V1》。

本文档主要回答以下问题：

1. 新量表第一阶段是否继续使用现有 `assessment_results` 主表；
2. 新量表与离婚力量表如何通过 `assessment_type` 区分；
3. 新量表特有结构如何放入 `result_payload`；
4. 前台提交时建议写入哪些字段；
5. 后台列表页如何识别、展示、筛选新量表记录；
6. 后台详情页如何根据量表类型分流展示；
7. CSV 导出如何补充新量表字段；
8. 第一阶段如何避免新量表记录误用离婚力量表详细报告逻辑；
9. 第一阶段暂不做哪些后台和数据库扩展。

本文档不是：

- Supabase SQL 迁移脚本；
- Codex 开发 prompt；
- 前端题库配置文件；
- 结果页文案主档；
- 后台 A4 详细报告方案；
- 完整多量表平台架构设计。

后续进入开发前，可在本文档基础上单独输出：

- 数据库字段检查与迁移建议；
- Codex 只读检查 prompt；
- Codex 分批开发 prompt；
- 验收清单。

## 2. 当前后台与数据库起点

### 2.1 既有项目结构

当前项目采用同仓库结构：

- 根目录：公开前台测评项目；
- `apps/admin-mvp/`：内部后台子项目；
- Supabase：数据库与数据存储；
- `assessment_results`：当前测评结果与线索主表。

当前离婚力量表已经完成：

- 前台作答结果写入 Supabase；
- 联系方式写入；
- `dimension_scores` 写入；
- 后台列表页；
- 后台筛选；
- 后台详情页；
- 后台跟进字段；
- CSV 导出；
- 单条详细报告页；
- A4 报告预览；
- 移动端长图报告；
- PNG / PDF 导出。

### 2.2 当前第一阶段目标

本次新量表第一阶段后台与数据库目标不是建设完整多量表平台，而是在现有后台与主表基础上完成最小可用适配：

1. 新量表结果能写入现有主表；
2. 后台列表能识别这是新量表记录；
3. 后台列表能按量表类型筛选；
4. 后台详情页能查看新量表基础结果；
5. 后台跟进字段继续可用；
6. CSV 导出能包含新量表关键字段；
7. 新量表记录不会误进入离婚力量表详细报告页。

## 3. 总体数据结构策略

### 3.1 第一阶段继续使用现有主表

第一阶段建议继续使用现有主表：

`assessment_results`

暂不新建新量表独立主表。

理由：

1. 当前后台已经围绕 `assessment_results` 形成稳定列表、详情、跟进和导出能力；
2. 新量表第一阶段仍属于测评线索收集与基础结果查看；
3. 两套量表都服务于婚姻家事业务线索管理；
4. 共用主表便于律所内部统一查看和跟进；
5. 第一阶段新建独立主表会增加后台查询、筛选、导出和权限适配成本；
6. 新量表特有结构可以通过 `result_payload` 承接，避免主表无限膨胀。

### 3.2 第一阶段新增字段原则

第一阶段建议只新增或启用少量通用字段：

1. `assessment_type text`；
2. `result_payload jsonb`。

其中：

- `assessment_type` 用于区分量表类型；
- `result_payload` 用于保存新量表特有结果结构；
- 其他共用字段继续沿用现有主表字段。

### 3.3 不建议第一阶段新增的表

第一阶段不建议新增：

- `narcissism_assessment_results`；
- `assessment_types`；
- `assessment_questions`；
- `assessment_reports`；
- `assessment_report_files`；
- `assessment_followup_logs`；
- `assessment_export_logs`；
- `staff_profiles`；
- `clients`；
- `service_orders`。

上述表可作为后续多量表平台化、报告持久化、多人协作、客户管理或正式 CRM 化时的扩展方向，但不属于第一阶段必做项。

## 4. assessment_type 字段方案

### 4.1 字段用途

`assessment_type` 用于标识每条记录来源于哪一套量表。

第一阶段建议使用字符串稳定代码。

建议取值：

| assessment_type | 含义 | 说明 |
|---|---|---|
| `divorce_readiness` | 离婚力量表 | 既有量表，可后续补齐 |
| `spousal_narcissism_risk` | 配偶高自恋特质与高冲突婚姻风险自测量表 | 新量表 |

### 4.2 历史记录兼容

当前离婚力量表历史记录可能没有 `assessment_type` 字段，或字段为空。

第一阶段后台应兼容：

- `assessment_type = null`；
- `assessment_type = ''`；
- `assessment_type = 'divorce_readiness'`。

建议显示时：

| 数据值 | 后台展示 |
|---|---|
| `spousal_narcissism_risk` | 配偶高自恋特质风险 |
| `divorce_readiness` | 离婚力量表 |
| `null` / 空字符串 | 离婚力量表 |
| 其他未知值 | 未知量表 |

说明：

- 为避免历史数据迁移风险，第一阶段可先不强制回填全部历史记录；
- 后台展示层将空值兼容为离婚力量表即可；
- 后续如需要统一数据口径，可再单独安排历史数据回填。

### 4.3 前台写入规则

新量表前台提交时必须写入：

`assessment_type = 'spousal_narcissism_risk'`

离婚力量表后续如有新提交，建议也逐步写入：

`assessment_type = 'divorce_readiness'`

但第一阶段开发第二量表时，不应为补齐离婚力量表写入口径而大幅改动旧主链路。可作为小范围兼容增强，由 Codex 只读检查后判断是否顺手补齐。

## 5. result_payload 字段方案

### 5.1 字段用途

`result_payload` 用于保存不同量表的特有结构化结果。

对于新量表，该字段用于保存：

- 总平均分；
- 分数方向；
- 高风险触发状态；
- 高风险触发题；
- 主要风险维度；
- 随机题目展示顺序；
- 后续可扩展的结果补充信息。

### 5.2 新量表 result_payload 建议结构

建议结构：

```json
{
  "average_score": 3.42,
  "score_direction": "higher_is_riskier",
  "high_risk_triggered": true,
  "high_risk_items": ["N5_Q34", "N5_Q37"],
  "primary_risk_dimensions": ["N5", "N4"],
  "question_order": ["N3_Q18", "N1_Q02", "N5_Q34"]
}
```

实际开发时：

- `question_order` 必须保存完整 40 个 `question_id`；
- `high_risk_items` 保存所有触发题目；
- 未触发高风险时，`high_risk_items` 应写入空数组；
- `primary_risk_dimensions` 建议保存 1–2 个维度代码；
- 展示文案由前端或后台根据代码映射生成，不在数据库中存长文案。

### 5.3 建议字段说明

| 字段 | 类型 | 含义 |
|---|---|---|
| `average_score` | number | 总平均分，范围 1.00–5.00 |
| `score_direction` | string | 分数方向，固定为 `higher_is_riskier` |
| `high_risk_triggered` | boolean | 是否触发高风险题 |
| `high_risk_items` | string[] | 触发的高风险题 `question_id` 列表 |
| `primary_risk_dimensions` | string[] | 主要风险维度代码 |
| `question_order` | string[] | 本次测评实际展示题序 |

### 5.4 后续可扩展字段

第二阶段或后续可考虑在 `result_payload` 中增加：

```json
{
  "risk_summary_version": "v1",
  "copy_version": "v1",
  "dimension_rankings": [
    { "dimension_code": "N5", "score": 3.88 },
    { "dimension_code": "N4", "score": 3.63 }
  ],
  "safety_notice_level": "triggered",
  "report_available": false
}
```

第一阶段不必强行增加上述字段。

## 6. 复用 assessment_results 既有字段

### 6.1 新量表建议写入字段总览

新量表第一阶段建议写入以下字段：

| 字段 | 建议写入值 | 说明 |
|---|---|---|
| `assessment_type` | `spousal_narcissism_risk` | 新量表类型 |
| `total_score` | 40–200 | 40 题实际总分 |
| `dynamic_full_score` | 200 | 固定满分 |
| `score_rate` | `total_score / 200 * 100` | 兼容后台字段 |
| `result_level` | `low` / `mild` / `moderate` / `high` | 四档风险代码 |
| `result_label` | 低风险 / 轻度风险 / 中度风险 / 高风险 | 中文展示标签 |
| `dimension_scores` | jsonb | 五维平均分 |
| `answers` | jsonb | 原始答案与实际计分 |
| `contact_name` | 用户填写 | 称呼 |
| `contact_phone` | 用户填写 | 手机号 |
| `contact_wechat` | 用户填写或空 | 微信号 |
| `submission_source` | `narcissism_risk_web` | 提交来源 |
| `follow_up_status` | `new` | 默认新线索 |
| `result_payload` | jsonb | 新量表特有结构 |

### 6.2 total_score

字段含义：40 题实际计分总和。

新量表口径：

- 普通题：实际计分 = 原始分值；
- 反向题：实际计分 = 6 - 原始分值；
- 总分范围：40–200。

后台展示：

- 可以展示为 `总分：137 / 200`；
- 但不应将其解释为“准备度分数”。

### 6.3 dynamic_full_score

字段含义：满分。

新量表口径：

`dynamic_full_score = 200`

原因：

- 新量表无跳题；
- 无“不适用”；
- 40 题全部必答；
- 每题最高 5 分。

### 6.4 score_rate

字段含义：得分率。

新量表计算方式：

`score_rate = total_score / 200 * 100`

注意：

- 该字段主要用于兼容后台既有列表、筛选或导出结构；
- 新量表前台和后台详情应优先展示总平均分；
- 不建议在新量表结果页突出展示得分率。

### 6.5 result_level 与 result_label

新量表四档映射：

| average_score | result_level | result_label |
|---|---|---|
| 1.00–1.80 | `low` | 低风险 |
| 1.81–2.60 | `mild` | 轻度风险 |
| 2.61–3.40 | `moderate` | 中度风险 |
| 3.41–5.00 | `high` | 高风险 |

注意：

- 新量表的 `high` 表示高风险；
- 离婚力量表的 `high` 或类似高分含义可能表示准备充分；
- 后台展示时必须结合 `assessment_type` 显示中文含义，避免混淆。

### 6.6 dimension_scores

新量表建议结构：

```json
{
  "N1": 3.25,
  "N2": 3.75,
  "N3": 2.88,
  "N4": 4.13,
  "N5": 3.50
}
```

后台展示时应映射为：

| 维度代码 | 展示名称 |
|---|---|
| N1 | 自我重要感与特权感 |
| N2 | 赞赏依赖与羞耻暴怒 |
| N3 | 共情缺损与责任外归因 |
| N4 | 操控剥削与第三方动员 |
| N5 | 高冲突升级与安全风险 |

### 6.7 answers

建议 `answers` 同时保存原始分值与实际计分。

示例：

```json
{
  "N1_Q01": {
    "raw_score": 4,
    "score": 4
  },
  "N1_Q07": {
    "raw_score": 4,
    "score": 2
  },
  "N5_Q34": {
    "raw_score": 5,
    "score": 5
  }
}
```

字段说明：

- `raw_score`：用户原始选择分值；
- `score`：完成反向计分后的实际得分；
- 反向题的 `raw_score` 与 `score` 不同；
- 高风险触发题根据 `raw_score` 判断。

### 6.8 submission_source

建议新量表写入：

`submission_source = 'narcissism_risk_web'`

后续如存在多个入口，可细化为：

- `narcissism_risk_web`；
- `narcissism_risk_edgeone`；
- `narcissism_risk_zunerguangsh`；
- `narcissism_risk_gpstrt`；
- `narcissism_risk_manual_test`。

第一阶段可先统一使用 `narcissism_risk_web`。

## 7. 后台列表页适配方案

### 7.1 当前列表页定位

后台列表页是内部人员查看所有测评线索的统一入口。

新增第二量表后，列表页应支持：

1. 同时展示离婚力量表与新量表记录；
2. 一眼识别每条记录属于哪套量表；
3. 按量表类型筛选；
4. 对不同量表采用正确的结果标签解释；
5. 展示新量表高风险触发状态；
6. 继续支持进入详情、跟进字段查看和 CSV 导出。

### 7.2 列表页新增展示字段

建议在列表页新增或调整以下展示：

| 字段 | 展示名称 | 说明 |
|---|---|---|
| `assessment_type` | 量表类型 | 离婚力量表 / 配偶高自恋特质风险 |
| `result_label` | 结果等级 | 对新量表展示低/轻度/中度/高风险 |
| `result_payload.average_score` | 总平均分 | 新量表优先展示 |
| `result_payload.high_risk_triggered` | 高风险触发 | 是 / 否 |

如果列表空间有限，可采用以下优先级：

1. 提交时间；
2. 姓名；
3. 电话；
4. 量表类型；
5. 结果等级；
6. 高风险触发；
7. 跟进状态；
8. 查看详情。

### 7.3 量表类型展示映射

建议后台展示映射：

```js
const ASSESSMENT_TYPE_LABELS = {
  divorce_readiness: "离婚力量表",
  spousal_narcissism_risk: "配偶高自恋特质风险",
  unknown: "未知量表"
}
```

兼容规则：

- `assessment_type` 为空时，按“离婚力量表”展示；
- 未知值按“未知量表”展示。

### 7.4 结果等级展示映射

离婚力量表与新量表的结果等级含义不同，因此不能只根据 `result_level` 展示颜色和文案。

建议后台显示时使用函数：

`getAssessmentResultDisplay(record)`

根据 `assessment_type` 分流：

#### 离婚力量表

沿用既有展示：

- 从容通关者；
- 稳健备战者；
- 急速蓄力者；
- 或当前代码中既有 result_label。

#### 新量表

展示：

- 低风险；
- 轻度风险；
- 中度风险；
- 高风险。

并可显示：

- 总平均分：例如 `3.42 / 5`；
- 高风险触发：是 / 否。

### 7.5 列表页新增筛选项

建议新增：

**量表类型筛选**

选项：

| 筛选值 | 展示 |
|---|---|
| `all` | 全部量表 |
| `divorce_readiness` | 离婚力量表 |
| `spousal_narcissism_risk` | 配偶高自恋特质风险 |

后台查询时应兼容历史空值：

- 筛选离婚力量表时，应包含 `assessment_type = 'divorce_readiness'` 或 `assessment_type is null`；
- 筛选新量表时，仅包含 `assessment_type = 'spousal_narcissism_risk'`。

### 7.6 新量表高风险筛选

第一阶段可选增强：增加“高风险触发”筛选。

选项：

| 筛选值 | 展示 |
|---|---|
| `all` | 全部 |
| `triggered` | 已触发高风险题 |
| `not_triggered` | 未触发高风险题 |

如开发复杂度较高，可暂不做该筛选，但列表页和 CSV 导出应展示该字段。

### 7.7 列表页颜色与标记

建议：

- 新量表“高风险”可使用醒目标记；
- 高风险触发可单独显示标签：`已触发高风险题`；
- 不建议仅靠颜色表达，必须有文字标签；
- 不要将新量表高风险和离婚力量表高分混用同一视觉语义。

## 8. 后台详情页适配方案

### 8.1 详情页分流原则

后台详情页应根据 `assessment_type` 判断展示结构。

建议逻辑：

1. 若 `assessment_type = 'spousal_narcissism_risk'`，展示新量表详情结构；
2. 若 `assessment_type = 'divorce_readiness'` 或为空，展示离婚力量表既有详情结构；
3. 若为未知值，展示基础信息，并提示“未知量表类型”。

### 8.2 新量表详情页模块结构

新量表详情页第一阶段建议包括以下模块：

1. 基础信息；
2. 测评结果摘要；
3. 五维风险均分；
4. 高风险触发信息；
5. 原始作答详情；
6. 后台跟进信息；
7. 内部备注；
8. 建联补充信息；
9. 详细报告入口占位提示。

### 8.3 模块一：基础信息

展示：

- 姓名 / 称呼；
- 电话；
- 微信；
- 提交时间；
- 提交来源；
- 量表类型。

量表类型展示：

> 配偶高自恋特质与高冲突婚姻风险自测量表

或短版：

> 配偶高自恋特质风险

### 8.4 模块二：测评结果摘要

展示：

- 风险等级；
- 总平均分；
- 总分 / 满分；
- 得分率；
- 主要风险维度；
- 高风险触发状态。

建议展示格式：

| 指标 | 示例 |
|---|---|
| 风险等级 | 高风险 |
| 总平均分 | 3.42 / 5 |
| 总分 | 137 / 200 |
| 得分率 | 68.50% |
| 主要风险维度 | 高冲突升级与安全风险、操控剥削与第三方动员 |
| 高风险触发 | 已触发 |

说明：

- 得分率可展示，但不作为重点解释；
- 总平均分应优先展示；
- 高风险触发状态应清晰可见。

### 8.5 模块三：五维风险均分

## 11. 旧详细报告逻辑隔离方案

### 11.1 当前风险

4. PDF / PNG 导出内容错误；
5. 后台人员误以为新量表已有详细报告能力。

### 11.2 第一阶段隔离原则

第一阶段必须确保：

- 新量表记录不进入离婚力量表详细报告逻辑；

- 若是新量表记录，应提示“新量表详细报告将在第二阶段接入”，而不是渲染旧报告。

### 11.3 直接访问 report 路由的处理

建议 `/leads/[id]/report` 页面读取记录后判断：

- 若为离婚力量表：正常展示现有详细报告；

## 12. 数据查询与筛选注意事项

### 12.1 列表查询

列表查询应支持 `assessment_type` 筛选。

筛选逻辑：

- 全部：不限制；
- 离婚力量表：`assessment_type = 'divorce_readiness'` 或 `assessment_type is null`；
- 新量表：`assessment_type = 'spousal_narcissism_risk'`。

### 12.2 result_payload 查询

若 Supabase 查询中直接按 `result_payload.high_risk_triggered` 筛选较复杂，第一阶段可暂不做高风险筛选。

优先级：

1. 列表展示高风险触发；
2. CSV 导出高风险触发；
3. 详情页展示高风险触发；
4. 后续再考虑高风险筛选。

如果 Codex 判断实现成本较低，可纳入同轮开发；否则放到后续小任务。

### 12.3 排序

列表仍按提交时间倒序排列。

不建议第一阶段按风险等级或高风险触发排序，避免增加查询和 UI 复杂度。

## 13. 字段空值与历史数据兼容

### 13.1 assessment_type 为空

兼容为离婚力量表。

### 13.2 result_payload 为空

可能出现在：

- 历史离婚力量表记录；
- 尚未升级写入逻辑的记录；
- 测试数据。

后台应避免因 `result_payload` 为空而报错。

新量表记录如果 `result_payload` 为空，应展示：

> 该记录缺少新量表扩展结果数据，请检查提交版本或数据写入逻辑。

### 13.3 dimension_scores 为空

离婚力量表历史记录中可能存在 `dimension_scores` 为空并通过 fallback 补算的逻辑。

新量表第一阶段建议前台必须写入 `dimension_scores`。

若新量表记录缺失 `dimension_scores`，后台可提示：

> 该记录缺少维度均分数据。

第一阶段不强制为新量表实现复杂 fallback 补算；如果实现成本低，可根据 `answers` 与题库配置补算。

### 13.4 answers 结构异常

如果 `answers` 缺失、题目不足 40 个或结构不符合新量表格式，后台详情应优雅降级：

> 原始答案数据不完整，无法完整展示逐题作答。

不要导致整个详情页崩溃。

- 不在列表页展开完整题干，避免敏感信息过度外露；
- 在详情页展示完整内容；
- CSV 导出应视为内部敏感文件；
- 后续正式上线时应加强后台账号、权限和导出管理。

## 18. 阶段性结论

本方案确认：

1. 新量表第一阶段继续使用现有 `assessment_results` 主表；
2. 通过 `assessment_type` 区分离婚力量表与新量表；
3. 通过 `result_payload` 保存新量表特有结构；
4. 后台列表页做量表类型展示、筛选和高风险标记；
5. 后台详情页根据量表类型分流展示；
6. 新量表第一阶段只展示基础结果，不接入旧详细报告；
7. CSV 导出补充量表类型、高风险触发和主要风险维度；
8. 第一阶段不做新表、不做详细报告、不做通用引擎重构。

本阶段后台与数据库适配的核心目标是：

**让第二套量表产生的线索能够进入现有后台统一管理，同时不破坏离婚力量表已经稳定的前台、后台和详细报告能力。**

后续《配偶高自恋特质量表开发路径与验收清单 V1》应在本文档基础上，将开发任务拆成可交给 Codex 执行的分批路径，并明确每一批的本地验收、数据库验收、后台验收和 git 收口节点。
