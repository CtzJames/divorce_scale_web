# 离婚力量表后台 MVP 范围与数据口径草案

## 1. 文档目的

本草案用于在“离婚力量表网页端”下一阶段开发开始前，先明确后台 MVP 的：

1. 目标与边界；
2. 功能范围；
3. 数据口径；
4. 字段设计原则；
5. 状态流转规则；
6. 暂不纳入 MVP 的事项。

本草案的定位不是最终技术方案，也不是数据库迁移脚本，而是用于先把后台 MVP 的产品范围和数据语言统一下来，避免后续开发一开始就滑向完整 CRM、客户门户或复杂报告系统。

---

## 2. 背景与当前起点

当前项目的前台测评主链路已基本完成，已经具备：

- 用户在线作答；
- 动态满分计算；
- 结果分级展示；
- 短板维度识别；
- 结果页内留资；
- 联系方式与测评结果同次写入 Supabase；
- GitHub Pages 可访问测试站；
- Supabase 后台表格化查看基础记录。

因此，下一阶段后台能力的第一目标，不是重做前台，也不是直接建设完整管理系统，而是先让律所内部相关人员能够：

- 查看客户线索；
- 识别优先级；
- 记录跟进；
- 标记服务走向；
- 导出和协同处理。

---

## 3. 后台 MVP 的核心目标

后台 MVP 只解决以下问题：

### 3.1 让律所内部能接住量表产生的线索

用户完成量表并提交信息后，后台应能够让法律顾问、律师或相关协作人员快速看到：

- 这是谁；
- 联系方式是什么；
- 测评结果大概如何；
- 当前是否已经有人跟进；
- 跟进到什么阶段；
- 下一步应由谁继续处理。

### 3.2 让后台记录从“静态收表”变成“可管理线索”

后台 MVP 的重点不是复杂分析，而是把当前 `assessment_results` 从单纯结果记录表，升级为可用于内部跟进和导出的基础线索主表。

### 3.3 为后续详细报告与客户授权查看预留扩展位

“详细报告生成”和“授权用户查看详细结果”是后续重要方向，但不应在后台 MVP 第一阶段就做成完整系统。

MVP 阶段应先预留字段和路径，不直接扩成完整客户门户。

---

## 4. MVP 阶段明确纳入范围的功能

### 4.1 后台记录列表页

后台首页应至少支持：

- 查看客户记录列表；
- 查看姓名、电话、微信、提交时间；
- 查看结果等级、得分率；
- 查看子女 / 跨境分流情况；
- 查看当前跟进状态；
- 查看当前负责人员；
- 查看服务类型；
- 查看最近更新时间。

### 4.2 列表筛选与搜索

后台 MVP 第一版建议支持以下筛选：

- 按 `follow_up_status` 筛选；
- 按提交时间区间筛选；
- 按结果等级筛选；
- 按是否有子女 / 是否跨境筛选；
- 按是否留电话 / 微信筛选；
- 按姓名 / 电话关键词搜索；
- 按负责人员筛选；
- 按服务类型筛选。

### 4.3 单条记录详情页

详情页建议支持查看：

- 用户基本联系方式；
- 测评总结果；
- 各维度得分信息；
- 用户原始作答数据；
- 当前内部跟进信息；
- 当前服务走向；
- 当前备注；
- 是否已开放详细报告查看权限。

### 4.4 可编辑字段

后台 MVP 第一版建议允许编辑以下信息：

- `follow_up_status`：当前跟进状态；
- `admin_note`：当前内部备注；
- `service_type`：当前拟提供 / 已进入的服务类型，可多选；
- `assigned_to`：当前主要负责人员；
- `appointment_owner`：当前约面或沟通主要对接人；
- `appointment_time`：已确认的沟通 / 约面时间；
- `report_visibility`：是否已允许用户查看详细报告；
- `report_version`：当前对应的详细报告版本。

其中，`service_type` 的产品含义应特别注意：

- 单次咨询属于短期服务；
- 离婚陪跑与长期咨询是两种不同逻辑的长期服务；
- 甄选服务在高净值 / 高复杂度场景下可作为叠加服务存在。

### 4.5 导出能力

后台 MVP 第一版建议支持：

- 按当前筛选条件导出 CSV；
- 导出基础字段 + 跟进字段；
- 不导出原始完整答案 JSON，除非后续确认有明确使用场景。

### 4.6 最小权限控制

后台 MVP 第一版至少应要求：

- 仅内部授权人员可访问后台；
- 不允许匿名访问；
- 不允许前台用户直接访问后台页面。

第一版暂不要求复杂角色权限，但应保留后续扩展空间。

---

## 5. MVP 阶段明确不纳入范围的功能

以下内容不建议在后台 MVP 第一阶段纳入：

### 5.1 完整 CRM 系统

暂不做：

- 客户多阶段商机漏斗系统；
- 自动提醒 / 自动分配；
- 复杂协作日志；
- 多维绩效统计；
- 全流程案件管理。

### 5.2 完整客户门户

暂不做：

- 用户登录后查看全部历史记录；
- 用户自行编辑个人信息；
- 用户在线与律师持续互动；
- 用户端复杂授权中心。

### 5.3 AI 自动深度报告系统

暂不做：

- 对每个客户实时大模型生成长报告；
- 后台自动批量生成高成本个性化报告；
- 未经律师确认即向用户开放完整分析。

### 5.4 复杂角色权限系统

暂不做：

- 按团队、部门、律师级别做复杂权限树；
- 字段级权限；
- 组织架构级可见性控制。

---

## 6. 后台 MVP 建议采用的数据结构策略

## 6.1 总体原则

后台 MVP 应优先遵循：

- 在现有 `assessment_results` 基础上尽量小步扩展；
- 避免第一阶段就拆成大量表；
- 先保证线索可查看、可编辑、可导出；
- 对未来详细报告、服务协同、授权查看预留扩展位。

### 6.2 第一阶段推荐方案

建议第一阶段仍以 `assessment_results` 作为线索主表。

在此基础上补充后台管理字段，而不是立刻拆出完整 CRM 多表结构。

原因：

- 当前前台提交已经稳定写入该表；
- 线索、结果、联系方式当前天然属于同一条记录；
- 先扩表比先重构更适合 MVP；
- 可显著降低迁移成本与开发复杂度。

### 6.3 第二阶段再考虑的扩展方向

若后续后台使用频率明显上升，再考虑新增：

- `assessment_followup_logs`：跟进日志表；
- `assessment_reports`：详细报告表；
- `staff_profiles`：内部人员映射表；
- `service_orders`：服务转化表。

但这些都不作为当前 MVP 必做项。

## 7. 线索主表的数据口径建议

以下字段分为四类：

1. 前台测评结果字段；
2. 用户留资字段；
3. 后台跟进字段；
4. 后续扩展预留字段。

### 7.1 前台测评结果字段

以下字段继续沿用现有口径：

- `total_score`
- `dynamic_full_score`
- `score_rate`
- `result_level`
- `result_label`
- `child_gate_answer`
- `cross_border_gate_answer`
- `weaknesses`
- `answers`
- `submission_source`
- `created_at`

这些字段原则上由前台写入，后台只读，不建议在后台人工修改。

### 7.2 用户留资字段

建议继续沿用：

- `contact_name`
- `contact_phone`
- `contact_wechat`

这些字段主要来源于前台提交。

后台如确需修改，应谨慎，只作为纠错用途，不应频繁手工改写原始留资内容。

### 7.3 后台跟进字段

建议新增或确认以下字段：

#### 7.3.1 `follow_up_status`

字段含义：
当前线索所处的跟进阶段。

建议类型：
字符串枚举。

建议第一版枚举值：

- `new`：新提交，未处理；
- `to_follow`：已查看，待联系；
- `contacted`：已联系，待回复 / 待进一步确认；
- `consulting`：已进入有效沟通或正式咨询安排中；
- `converted`：已转化为明确服务；
- `invalid`：无效线索 / 重复 / 无法联系 / 明确无意向。

建议规则：

- 前台插入新记录时默认值为 `new`；
- 后台编辑时必须从枚举中选择；
- 不允许自由输入文本替代状态。

#### 7.3.2 `admin_note`

字段含义：
当前线索的内部补充说明与处理备注。

建议类型：
长文本。

建议用途：

- 记录沟通结论；
- 记录风险点；
- 记录用户当前诉求；
- 记录下一步安排。

建议填写原则：

- 只写客观事实与处理信息；
- 不写情绪化评价；
- 不写与业务无关的私密内容；
- 不在其中替代状态字段；
- 不在其中替代服务类型字段。

建议模板：

`[日期 处理人] 本次沟通情况；用户当前核心诉求；当前判断；下一步安排。`

示例：

`[2026-04-17 Sandra] 已电话沟通。用户当前主要关注财产分割与孩子抚养安排，倾向先做一次正式咨询；下一步为下周确认面谈时间。`

#### 7.3.3 `service_type`

字段含义：
律所当前拟提供、正在提供或已进入的服务类型。

建议类型：
多选枚举，技术实现上可根据实际方案采用数组、关联表或可序列化结构。

结合当前业务理解，`service_type` 不宜按“单一互斥服务”理解，而应允许体现：

- 短期服务；
- 两种不同逻辑的长期服务；
- 在高净值 / 高复杂度场景下可叠加的甄选服务。

建议第一版枚举值：

- `none`：尚未进入明确服务；
- `single_consultation`：单次咨询；
- `divorce_escorting`：离婚陪跑；
- `long_term_consultation`：长期咨询；
- `screening_service`：甄选服务；
- `litigation_representation`：诉讼代理；
- `agreement_support`：协议离婚协助；
- `cross_border_support`：跨境婚姻 / 跨境身份专项支持；
- `other`：其他。

建议规则：

- 第一版即按多选设计；
- `divorce_escorting` 与 `long_term_consultation` 必须视为两种不同服务，不合并为一个泛化的长期支持大类；
- `screening_service` 可作为高净值 / 高复杂度客户的叠加型服务，不必理解为一定独立于其他服务单独存在；
- 若尚未明确服务方向，可仅标记 `none`；
- 若已进入组合型服务，可同时标记多个服务类型；
- 后续如需统计和关联能力更强，再升级为独立服务关联表。

#### 7.3.4 `assigned_to`

字段含义：
当前主要负责该线索的内部人员。

建议类型：
字符串。

第一版建议：
先允许写人员姓名或统一内部称呼，不必一开始就强绑定用户表。

后续如后台使用稳定，再升级为人员 ID 关联。

#### 7.3.5 `appointment_owner`

字段含义：
当前负责约面、约通话、推进下一步沟通的人。

说明：
该字段与 `assigned_to` 可以一致，也可以不同。

第一版不强制拆得很复杂，但建议保留独立字段，避免一个字段承担所有责任人含义。

#### 7.3.6 `appointment_time`

字段含义：
当前已确认的下一次正式沟通时间。

建议类型：
时间戳。

说明：
若尚未约定，则为空。

#### 7.3.7 `last_follow_up_at`

字段含义：
最近一次人工跟进时间。

建议类型：
时间戳。

建议规则：
后台更新状态或备注时同步更新。

#### 7.3.8 `updated_by`

字段含义：
最近一次修改后台信息的内部人员。

建议类型：
字符串。

第一版可先记录名字；后续再绑定真实账号 ID。

### 7.4 详细报告与授权查看的预留字段

#### 7.4.1 `report_visibility`

字段含义：
用户当前是否被允许查看详细报告。

建议枚举：

- `hidden`：默认隐藏；
- `internal_only`：仅内部可见；
- `user_visible`：已开放给用户查看。

建议默认值：
`hidden` 或 `internal_only`。

当前建议：
第一阶段默认不向用户开放详细报告，因此推荐默认 `internal_only`。

#### 7.4.2 `report_version`

字段含义：
当前线索所对应的详细报告版本编号。

建议用途：
便于后续报告模板迭代时知道该客户看到的是哪一版内容。

#### 7.4.3 `report_generated_at`

字段含义：
详细报告最近一次生成时间。

第一阶段可先预留，不一定立即启用。

## 8. `follow_up_status` 的状态流转建议

后台 MVP 第一版建议采用轻量状态流，而不是复杂漏斗系统。

建议流转如下：

`new` → `to_follow` → `contacted` → `consulting` → `converted`

并允许任一阶段进入：

`invalid`

### 8.1 各状态定义

#### `new`

定义：
前台新提交，后台尚无人处理。

进入条件：
新记录默认进入。

#### `to_follow`

定义：
内部已看到这条记录，认为值得继续联系，但尚未完成有效联系。

适用场景：

- 已分配负责人；
- 待电话 / 微信联系；
- 等待合适时间触达。

#### `contacted`

定义：
已发起联系，已建立初步沟通，但尚未进入稳定咨询推进。

适用场景：

- 已电话 / 微信联系；
- 用户仍在考虑；
- 待用户回复；
- 待补充资料。

#### `consulting`

定义：
已进入明确的进一步沟通或服务判断阶段。

适用场景：

- 已约正式咨询；
- 已进行较深入沟通；
- 正在判断服务方案。

#### `converted`

定义：
已形成明确服务承接。

适用场景：

- 已购买咨询；
- 已签约服务；
- 已进入正式案件推进。

#### `invalid`

定义：
该记录不再作为有效线索继续推进。

适用场景：

- 明确无意向；
- 无法联系；
- 重复提交；
- 明显无效信息；
- 非目标客群。

### 8.2 状态使用规则

建议遵循：

- 一个线索同一时点只能有一个主状态；
- 备注记录具体过程，状态反映当前阶段；
- 不使用自由文本状态；
- 不额外再造“若干近义状态”，防止后期无法筛选统计。

## 9. `admin_note` 的填写口径建议

### 9.1 目标

`admin_note` 不是聊天记录备份，也不是案情全文记录，而是内部协作所需的“当前判断与下一步信息”。

### 9.2 建议记录内容

建议优先记录：

- 当前核心诉求；
- 已完成的联系动作；
- 用户当前态度与阶段；
- 当前主要风险点；
- 下一步动作；
- 需要谁接手。

### 9.3 不建议记录的内容

不建议写入：

- 与业务无关的主观评价；
- 侮辱性、情绪化表达；
- 不必要的个人隐私；
- 与字段重复的内容；
- 不能核实的法律判断。

### 9.4 推荐写法

建议采用固定结构：

`[日期 处理人] 已做动作；用户当前情况；关键判断；下一步。`

### 9.5 后续升级方向

若后台使用频率提高，后续应考虑将 `admin_note` 从单一文本升级为独立跟进日志表；
但在 MVP 阶段，先用单字段承载最小协作信息即可。

---

## 10. 服务类型字段的口径建议

### 10.1 目标

`service_type` 用于回答：

“这条线索目前在律所内部被判断为更接近哪些服务承接方向？”

它不是最终收费字段，也不是正式订单系统字段。

### 10.2 当前业务口径理解

结合现有客户分流规则，服务类型应理解为：

- 短期服务可包含单次咨询；
- 长期服务中，离婚陪跑与长期咨询是两种不同服务，不应混同；
- 对高净值、高复杂度客户，可在主服务之外叠加甄选服务；
- 因此 `service_type` 更适合按多选设计，而不是互斥单选。

### 10.3 第一版建议值

建议采用多选：

- `none`
- `single_consultation`
- `divorce_escorting`
- `long_term_consultation`
- `screening_service`
- `litigation_representation`
- `agreement_support`
- `cross_border_support`
- `other`

### 10.4 使用原则

- 尚未明确前，用 `none`；
- 若当前仅进入一次性短期承接，可标记 `single_consultation`；
- 若客户具备较好的离婚意愿与推进能力，且需要持续承接和推进，可标记 `divorce_escorting`；
- 若客户短期内不一定立即离婚，或当前更需要持续认知、准备与判断支持，可标记 `long_term_consultation`；
- 若客户为高净值、高复杂度客群，需要额外专业资源筛选、匹配和协调，可叠加 `screening_service`；
- 第一版即应支持组合型服务；
- 若后续需要更细的统计、结算或流程联动，再升级为关联结构。

### 10.5 `service_type` 的推荐存储格式

当前建议：

**在 Supabase / Postgres 中，第一版优先使用“文本数组（text[]）”存储 `service_type`。**

即一条记录可写成类似：

- `['divorce_escorting']`
- `['long_term_consultation', 'screening_service']`
- `['single_consultation']`

推荐原因如下：

#### 1. 最贴合当前业务形态

`service_type` 当前是一个“固定代码集合中的多选字段”，而不是高度自由的复杂对象。

也就是说，你们现在需要表达的是：

- 这条线索命中了哪些服务类型；
- 一个客户可以同时命中多个服务类型；
- 这些类型本身是预先约定好的稳定代码。

对于这种需求，文本数组已经足够。

#### 2. 比 JSON 更规范、更容易约束

如果用 JSON，也能存多选值，但会带来几个问题：

- 更容易写入不统一的数据结构；
- 更容易混入对象、中文文案、临时字段；
- 后续筛选、统计、导出时更容易出现口径不一致。

而 `text[]` 更明确地告诉开发和后台：

“这里存的就是一组服务类型代码，不是别的。”

#### 3. 比独立关联表更轻，适合当前 MVP

如果现在就拆成独立关联表，当然会更“标准化”，但会明显增加：

- 表结构复杂度；
- 查询复杂度；
- 后台编辑复杂度；
- 开发成本。

当前阶段你们最重要的是：

- 先让后台能看、能改、能筛、能导；
- 先快速跑通内部使用。

因此不建议第一版就为了“理论上更标准”而把结构做重。

#### 4. 便于后续升级

未来如果 `service_type` 真发展成：

- 需要记录服务开始时间；
- 需要记录主服务 / 次服务；
- 需要记录报价、成交、结束时间；
- 需要做复杂统计和流转；

那时再把它升级成独立关联表即可。

也就是说：

**`text[]` 很适合作为当前 MVP 的过渡型正式方案。**

### 10.6 当前推荐的数据填写规则

为避免数据变乱，建议在第一版中固定只允许写入以下代码：

- `none`
- `single_consultation`
- `divorce_escorting`
- `long_term_consultation`
- `screening_service`
- `litigation_representation`
- `agreement_support`
- `cross_border_support`
- `other`

后台展示时可以把这些代码映射成中文名称，但数据库中建议始终存英文稳定代码。

## 11. 详细报告在 MVP 中的建议处理方式

### 11.1 当前判断

“详细报告生成”和“授权用户查看”属于重要方向，但不应成为后台 MVP 第一阶段的主开发对象。

### 11.2 建议拆成两步

#### 第一步：内部版详细分析

先基于规则生成一份内部可读的详细分析内容，用于：

- 内部快速理解客户状态；
- 辅助后续沟通；
- 作为后续正式详细报告的底稿；
- 支持内部导出与流转。

这一步优先考虑规则型结构化报告，而不是 AI 自由生成长文。

#### 第二步：授权用户查看

待内部版内容稳定后，再做：

- 是否开放给用户；
- 何时开放；
- 由谁审核；
- 用户看到的是哪一版。

### 11.3 MVP 阶段结论

后台 MVP 第一阶段：

- 详细报告第一版先只做内部可见；
- 后台应支持内部查看详细分析；
- 后台应支持内部导出详细报告；
- 可预留 `report_visibility`、`report_version` 等字段；
- 可在详情页设置“详细报告”模块；
- 不把“用户授权查看系统”纳入第一阶段强制范围。

## 16. 当前已确认事项

### 16.1 服务类型第一版按多选实现

当前已确认：

- 服务类型第一版按多选设计；
- 律所实际业务中，单次咨询属于短期服务；
- 离婚陪跑与长期咨询是两种不同的长期服务，不应合并理解；
- 高净值 / 高复杂度客户可在主服务之外叠加甄选服务；
- 因此不再按单选口径设计，也不再使用会混淆两类长期服务的泛化命名。

### 16.2 `assigned_to` 与 `appointment_owner` 需要分开

当前已确认：

- 按律所实际业务经验，`assigned_to` 与 `appointment_owner` 需要分开；
- `assigned_to` 表示当前主要负责该线索推进的人；
- `appointment_owner` 表示当前负责约面、约通话或推进下一步沟通安排的人。

### 16.3 详细报告第一版先只做内部可见

当前已确认：

- 详细报告第一版只做内部可见；
- 后台应支持内部导出；
- 暂不对用户开放查看。

### 16.4 后台第一版暂不需要复杂登录权限

当前已确认：

- 后台第一版只做最小鉴权；
- 暂不建设复杂角色权限系统；
- 后续再根据实际使用情况升级。

## 17. 阶段性结论

后台 MVP 第一阶段的本质，不是建设完整 CRM，也不是立即建设客户门户，而是：

- 把量表前台产生的线索接住；
- 把测评记录转成可管理记录；
- 让内部人员能看、能筛、能改、能导；
- 为后续详细报告与用户授权查看预留结构。

因此，当前最合理的后台 MVP 开发边界应为：

**基于 `assessment_results` 扩展后台管理字段 + 建立后台列表 / 筛选 / 详情 / 编辑 / 导出能力。**

而“详细报告生成”和“授权用户查看”应作为后台 MVP 之后的下一阶段能力继续推进。
